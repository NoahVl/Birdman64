# Controller input (`crates/birdman64/src/input.rs`)

- **Path:** thread `pw64-input` polls `gilrs` every 4 ms, merges all connected pads + held keys into one N64 pad, and calls `pw64_platform::headless::set_controller1` (one `AtomicU32`: `button | x<<16 | y<<24`). `osContGetReadData` delivers it as controller 1 and logs `[input] first non-idle pad delivered` once. `PW64_NO_INPUT` = no thread (idle pad, old headless behaviour).
- **Controller 1 only.** `osContInit` pattern stays `1`: the game reads it once in `uvControllerInit` (`gControllerPattern`), only pad 0 is used (`game.c` checks `uvControllerCheckInserted(0)`), and it is single-player. Extra gamepads merge into pad 1 (buttons OR'd, larger stick wins).
- **Game-side stick handling** (`uvReadController`, kernel/system.c): per axis, |v| < 7 → 0, saturates at 68 (x) / 70 (y), result `(v∓7)/61` (x) or `/63` (y). No other code reads `gControllerPads`.
- **Stick mapping** (`stick_to_n64`): radial deadzone 0.12, remaining magnitude rescaled to 0..1, then per axis `±(7 + |a|·73)`, clamped to ±80. The +7 offset means the host deadzone *replaces* the game's (no stacking); cardinal saturation at ~84% deflection. **Octagon gate:** the scaled vector is stretched onto the N64 octagon (corner 0.875 → ~71,71), keyboard diagonals too: the game saturates each axis at 68/70 so on hardware a full diagonal is full on both axes. Before, round diagonals (59,59) read 0.83/axis → the hang glider's squared stick curve (`D_80367F60`) left ~68 % pitch authority while steering: the glider lifted while diving through the Chicken Dive rings (replay of a recorded playtest: nose −0.90 → −0.70 during left+up; with the gate it stays −0.91…−0.94).
- **Gamepad (positional; Nintendo layout matches by position):** South=A, West/East=B, North=C-up, LT/ZL (analog ≥0.3)=Z, LB/L=L, RB/R and RT/ZR=R, Start=Start, D-pad (buttons or hat axes)=D-pad, right stick (≥0.5)=C buttons, left stick=stick.
- **Keyboard:** WASD/arrows=stick (full, diagonals normalized), Space=A, LShift=B, Z/LCtrl=Z, Q=L, E=R, Enter=Start, I/J/K/L=C up/left/down/right, T/F/G/H=D-pad. Wired: `window.rs` feeds winit `KeyboardInput` (physical keys) to `input::on_key`; focus loss → `release_all_keys`. F11 / Alt+Enter toggle borderless fullscreen (not forwarded; plain Enter is Start). Button bindings (keyboard and gamepad) are configurable in `pw64.toml` — `[input.keyboard]` / `[input.gamepad]` per-slot entries (e.g. `A = "Space"`), overriding that slot's defaults; the keyboard stick directions are slots too (`STICK_UP/DOWN/LEFT/RIGHT`), so binding a slot to W/A/S/D/arrows gives that button only (the key comes off the stick). Resolution (`input::resolve`): slot names case-insensitive; unknown slot/name warns once at startup; an explicitly bound input is removed from every other slot's defaults (`R = "ZL"` moves ZL off Z — Z shows "(unbound)"); the same input bound explicitly to two slots presses both; the settings pad button is never bound. **Settings screen (settings.md): F10 + pad Select (config `[input] settings_key` / `settings_pad_button`) are consumed by the overlay — unmapped slots by construction; while it is open, `publish` routes the merged pad to the overlay and gives the game an idle pad. `input::overlay_toggled` re-publishes on open/close (the poll loop only publishes on change); on close, buttons still held are masked from the game until released (`Sources::suppressed`), so the A/Start that closed the overlay doesn't reach the game as a fresh press.**
- **Scripted input** (`PW64_INPUT_SCRIPT=<file>`, windowed or headless): a third source merged into the pad like the others. `input::script_tick(retrace)` runs from the game thread's retrace hook. Line format: `<retrace|+delta> [A B Z START L R CU CD CL CR DU DD DL DR] [stick X,Y]` (case-insensitive, `#` comments, raw N64 stick -80..80, y up), held until the next line; an empty step = release. Bad script → exit 2. Example: `crates/birdman64/scripts/fly_hang_glider.txt` (title menu is up at ~retrace 1000; one A every 100 retraces walks start → file → class → pilot → summary → Start).
- **Recording** (`PW64_RECORD_INPUT=<file>`, windowed or headless): writes the pad the game sees (after the overlay/suppression masks) as an input script, one step per change at the retrace it took effect — replay with `PW64_INPUT_SCRIPT` (+ a copy of the same save via `PW64_EEP`). A scripted run records back identically; live input lands on the next 60 Hz retrace (≤16 ms late), so long replays of live play can drift from the original flight.
- gilrs 0.11 on Windows uses Windows.Gaming.Input: Xbox pads natively, DS4/DualSense/Switch Pro as raw controllers via the bundled SDL mapping DB (mapping source logged on connect). Hot-plug handled by re-enumerating every poll. Untested with real hardware so far; if pads don't register without a focused window (WGI quirk), try gilrs' `xinput` feature for Xbox pads.

## Switch 2 pads over BLE (`crates/birdman64/src/ble.rs`)

- **Protocol reality (differs from what one might assume):** Switch 2 pads do **not** use HID-over-GATT (0x1812/0x2A4D) — they expose a proprietary GATT service: input-report characteristic `ab7de9be-89fe-49ad-828f-118f09df7fd2` (notify, 63-byte reports), command write `649d4ac9-…f005`, command response `c765a961-…836a`. Pads connect unpaired (no pairing handshake needed to stream). Report layout: u32 LE timestamp [0..4], u32 LE button bitmask [4..8], two 3-byte packed sticks (12-bit LE: x low, y high, center 2048) at [10..16]. Source: `trevlars/switch2-controllers-linux` (MIT; credits `Nadeflore/switch2-controllers`). SDL's `SDL_hidapi_switch2.c` deliberately does **not** support these pads over Bluetooth.
- **btleplug** (WinRT GATT backend on Windows) + `futures` (executor-agnostic, no async runtime; btleplug's tokio `broadcast` channels need no runtime). Thread per pad ("pw64-pad") runs `connect` → `discover_services` → handshake writes → subscribe input char → report pump into a static `Slots` array; a "pw64-ble" scanner thread claims new pads every 3 s and gives them back on disconnect (sleep/wake reconnects). Raw stick y already grows **upward** (verified on a real Joy-Con 2; the original "invert like SDL" was wrong — SDL negates only because its y points down), so no flip at decode. Player LED: command `0x09`/sub `0x07`, data[0] = LED bitmask, 8 data bytes (player 1 → 0x01), ends the pairing sweep. Sent straight after the feature writes it was sometimes ignored (real Joy-Con 2), so it goes out from the report loop and is resent every 300 ms (≤10×, `LedRetry`) until a command-response notification starting with `0x09` arrives; log `player LED set (after n send(s))`.
- **btleplug WinRT pitfalls (from its 0.11.8 source):** `Peripheral::notifications()` is a broadcast owned by the peripheral — it **never ends on disconnect**; the pump selects it with `adapter.events()` and stops on `CentralEvent::DeviceDisconnected(id)` (else the last report — held buttons/stick — sticks forever and the pad never reconnects). `Manager::adapters()` builds a new watcher + radio `StateChanged` handler per call and `start_scan` adds another `Received` handler per call (neither removed): get adapters once, scan once. After a disconnect the adapter drops the peripheral and re-lists it as a new one on the next advertisement.
- **Virtual pad (`ble::*_MAP` tables, Nintendo labels: A east, B south, X north, Y west):** L Joy-Con → left stick + arrows→D-pad, L/SL/SR→L, ZL→Z, minus→Start; R Joy-Con → right stick→C buttons + A→A, B/Y→B, X→C-up, R/ZR/SL/SR→R, plus→Start; Pro Controller 2 → R Joy-Con face table + L, ZL→Z, R/ZR→R, D-pad, both sticks. Pads merge via `Pad::merge` (buttons OR'd, larger main stick wins). Label-based (Nintendo A → N64 A), unlike the positional gilrs defaults — a choice, confirm feel on hardware. Sticks go through the same radial-deadzone `stick_to_n64`.
- **Enable:** default OFF. `PW64_BLE=1` (or `0` to disable; invalid value warns and falls through) > `[input.ble] enabled = true` in `pw64.toml` > off. Players switch it in Settings > Controls > "Switch 2 controllers (Bluetooth)" (live, auto-saved to `[input.ble] enabled`; Off = default, key removed). Row is disabled with a reason when `PW64_BLE` or `PW64_NO_INPUT` is set.
- **Runtime switch (`ble::set_enabled`):** `ble::init()` (main, only without `PW64_NO_INPUT`) marks BLE available and applies the startup value. `ON` AtomicBool; the scanner thread is spawned lazily on the first switch-on (`OnceLock<Thread>`) and never exits. It fetches adapters once (re-fetching leaks WinRT watchers); per cycle it follows `ON`: on → `start_scan` once + claim pads; off → `stop_scan` + `disconnect` every claimed peripheral (btleplug emits `DeviceDisconnected` for local disconnects, ending pad threads), then `park()`. `set_enabled` unparks it, so it reacts at once. Each re-enable registers one more WinRT advertisement handler (bounded by player toggles; the per-cycle leak was the problem). Off also clears `STATE` immediately; `pad()`/`any_connected()` return idle while off; `set_slot` drops late reports; pad threads break on the next event when off and don't retry. No adapter → status `NoAdapter`, retried every 10 s while on.
- **Status (`ble::status()`):** Off / Starting / NoAdapter / Searching / Connected(names) — shown under the settings row (`settings::ble_status_lines`, with the "press Sync, don't pair in Windows" hint while searching). "Connected" = slot has a report. Needs the input thread (`PW64_NO_INPUT` disables BLE too). Diagnostic: `PW64_BLE_LIST=1` scans 8 s, prints every device (name/addr/RSSI/services/manufacturer data), marks Switch 2 pads, exits — no ROM needed.
- **Discovery (verified on real Joy-Con 2):** in Sync mode they advertise **no local name**, only manufacturer data under Nintendo's company id `0x0553`: `01 00 03 | 7e 05 | 66 20 | …` = USB vendor 0x057E + product u16 LE at bytes 3..7 (0x2066 Joy-Con R, 0x2067 L, 0x2069 Pro 2; 0x2073 NSO GC unmapped). `classify_props`: name first, else that product id. Name-only matching found nothing.
- **Stick range (real Joy-Con 2):** the stick stops far short of the 12-bit range, so the nominal /2048 scaling made a full push ~60%: slow steering vs the keyboard and the results menu (needs |y| > 0.75, results.c) never moved. `StickCal` auto-ranges per connection: each axis direction scales to the furthest travel seen (floor 1050 raw). Measured full pushes (one L+R pair): L stick −x 1210 +x 1250 −y 1171 +y 1332; R stick −x 1180 +x 1205 −y 1282 +y 1112 (nominal 2048 → full push read ~0.6). Log: `stick travel -[..] +[..]` as ranges grow. Reading the pad's factory calibration would replace it.
- **Switch 1 pads ("Joy-Con (L)", "Pro Controller") deliberately not matched** — they speak BLE HID with a different report format.
- **Tested on Joy-Con 2 only:** WinRT unpaired GATT connect, the handshake (command-response CCCD subscribe + feature init/enable `0x0C`/0x02, 0x04 with flags 0x07, in `ble::handshake`) and input streaming verified on a Joy-Con 2 pair. Open: BLE connection interval (~20 Hz claimed on Win10) vs the game's 30 Hz input; button mapping (SL/SR→L/R, minus→Start on the L half) is a choice, not research.
- **Unit tests** (no hardware): report parse/rejects-short, stick normalize/invert, per-side button tables, L+R merge, Pro d-pad, name classification, 0x91 command framing (`ble::tests`). Settings over BLE: minus (= Select, the gilrs default), Home (bit 12) and Capture (bit 13) → `ble::settings_pressed`, edge-detected in the input thread with the gilrs settings button; never reach the game. Minus used to double as Start on the L half — dropped (a lone L has no A anyway).
- **Test instructions for real pads:** 1) `PW64_BLE_LIST=1` with pads in range → pads listed and marked "Switch 2 pad"; if not, they're bonded to a console — hold Sync. 2) `PW64_BLE=1` in a windowed run → `[ble] connecting to …`, `[ble] …: streaming input reports`; move sticks / press A, B, ZL, ZR, minus, plus, X and compare with the game (settings screen / on-screen response). 3) Same with a Pro Controller 2. 4) Both Joy-Cons together → one pad, L stick steers, R stick = camera. 5) Sleep/wake a pad mid-run → reconnects within ~6 s. 6) Headless scripted run with `PW64_BLE=1` still passes (BLE idle pad must not disturb it).

## Live rebinds + pad capture

- **State:** `KEYBOARD`/`GAMEPAD` are `LiveTable`s: one `Mutex<Option<Live>>` each (override map + `Arc<Vec<Binding>>`, built from config on first use). Readers (`key_mapping`, `gamepad_pad` every 4 ms) clone the `Arc` (`snapshot`) and scan unlocked; `bind`/`edit` swap in a new `Arc`. No guard escapes `LiveTable::with` (an earlier `RwLock` version self-deadlocked when a read guard lived across a rebind). Rebinding a slot also drops its own override under any case spelling (`a = …` in pw64.toml).
- **Pad capture (used by the Controls page):** `start_pad_capture()` arms `PAD_CAPTURE`; the input thread's `EventType::ButtonPressed` arm stores the first pressed button (skips Unknown/Mode/the settings trigger) in `CAPTURED_BUTTON` and disarms; `take_captured_button()` takes once, `cancel_pad_capture()` drops. Bind/reset never touch the settings pad button (`resolve` reserved slot).
- Tests serialize global state with a `TEST_LOCK` Mutex; `rebind_conflict_and_reset` restores the pre-test maps in a `Drop` guard.

## Keyboard stick slots

- `KEYBOARD_SLOTS` includes `STICK_UP/DOWN/LEFT/RIGHT` (bits `1 << 16 .. 1 << 19`, names `STICK_UP` …, defaults W+ArrowUp / S+ArrowDown / A+ArrowLeft / D+ArrowRight, appended after the 14 button rows so the settings order is unchanged). `Binding.bit` and both slot tables are `u32` (`CONT_* as u32` in the const tables: `u32::from` is not const-callable); `bits_for` returns `u32`, and `key_mapping` splits a key's OR of bits: low 16 = CONT buttons, high = summed stick directions. `bits_for` still needs u32 because a `pw64.toml` override may bind one key to a stick slot and a button slot (bits > u16).
- One `resolve` pass: an override of a stick slot replaces its defaults like any slot (`STICK_UP = "KeyI"` leaves KeyW unbound), and binding a key to a button slot takes it off the stick defaults, so `A = "KeyW"` means A only (not A + stick up). Tests: `stick_slots_resolve_like_buttons`; `key_mapping` live checks inside `rebind_conflict_and_reset` (KeyW → `Some((CONT_A, 0, 0))` while bound to A, `(0, 0, 1)` after reset).

## What each N64 input does (from the decomp; for the Controls page)
Player-facing text (vehicle names as in the game; "?" items left out on purpose):
- **Stick:** steer / aim; menus: move the selection.
- **A:** menus: confirm. Rocket Belt: strong thrust. Gyrocopter: throttle up. Cannonball: fire. Birdman: flap. Jumble Hopper: jump (hold for higher). Skydiving (chute open): brake.
- **B:** menus: back. Rocket Belt: gentle thrust. Gyrocopter: throttle down. Skydiving: open the parachute.
- **Z:** Hang Glider / Birdman: hold to aim the camera, release to take a photo. Gyrocopter: hold to aim, release to fire a missile. Rocket Belt: cut thrust. Cannonball: fine aim. 3D map: hold to rotate the view.
- **R:** change the camera view (all vehicles).
- **C buttons:** look around; 3D map: C Up/Down zoom; photo album: C Left/Right previous/next.
- **Start:** pause; menus: confirm.
- **L, D-pad:** not used by the game (free to rebind).
Sources: each vehicle's `*MovementFrame` (hang_glider1.c, code_AC1A0.c rocket belt, code_7CF30.c gyrocopter, cannonball.c, birdman0.c, jumble_hopper.c, skydiving.c/code_BA190.c), snap.c (photos), map3d.c, menu_utils.c, game.c (pause). Hang Glider A/B set one shared flag (flare/brake?, unconfirmed: not shown to players).

## Pad family + active pad + pad art

- **Pad family** (`PadFamily`): Xbox / PlayStation / Nintendo / Generic. `pad_family(vendor, name)`: vendor id first (0x045E Microsoft, 0x054C Sony, 0x057E Nintendo), then a lowercase-name fallback (contains "xbox" / "playstation" / "ps4"/"ps5" / "nintendo"|"pro controller"|"joy-con"; gilrs names DS4 as "Wireless Controller", so the name fallback exists for pads with no vendor id). gilrs' `vendor_id()` may be `None` (WGI pads), so never assume it.
- **Active pad:** `input::active_pad()` returns the `PadInfo` (name + family) of the pad the player last touched, so the Controls page can draw that pad's family and `button_name` can use its labels. Seeded from the first connected pad at thread start; updated on `Connected` and on `ButtonPressed` (last used wins); on `Disconnected` it falls back to another connected pad, else `None`. BLE pads are not tracked for 1.0 (their connection is separate from gilrs). gilrs pitfall: `ButtonPressed(_, code)`'s second field is the button `Code`, not the pad id - use `ev.id`.
- **`button_name(b, family)`**: family-appropriate labels for the Controls page. Nintendo positional: South="B", Select=minus sign, Start="+"; Xbox names stand in for Generic; D-pad names are family independent; gilrs' extra `C`/`Z` Button variants (not in any match arm by default) return "C"/"Z".
- **Pad art (`crates/birdman64/src/pad_art.rs`)**: egui painter drawing of the N64 controller, scaled from a nominal 300x190 rect to the panel width; geometry in fractions via `parts(r)` (body/L/R grey, A blue/B green/C yellow circles, Z as a dashed outline rect labelled "Z (back)"). Highlight mode (per button or stick) = accent fill + 3 px white outline + 1.06 scale up. (The Controls page now uses the SVG / ROM-sprite drawing described in settings.md.)
- **egui 0.33 pitfalls (pad_art + settings use):** `Rect` has accessor methods (`rect.left()`, not struct fields); `Align2::CENTER_TOP` (not `TOP_CENTER`); there is no dashed-stroke primitive, dashes are faked with short line segments (`dashed_rect`). C-button directions must be painted as triangles: the default egui fonts have no arrow glyphs. `draw_painted_shapes` runs a real `egui::Context::run` in-process (no window) and inspects the paint list; `KEYBOARD_SLOTS`/`GAMEPAD_SLOTS` are now `pub(crate)` so pad_art tests can use slot names.
- `parse_key` accepts every winit `KeyCode` variant name via the `KEYCODE_NAMES` const table (194 entries, generated from winit 0.30.13; the round-trip test iterates it, so a missing entry cannot hide). `NumpadEnter` is its own key now (it used to alias `Enter` and break saved numpad bindings); `MetaLeft`/`MetaRight` alias `SuperLeft`/`SuperRight`. `parse_gamepad_button` gained gilrs `C` and `Z` (capture can save them). Bind saves `format!("{k:?}")`, so any new winit/gilrs variant needs a table/test entry.

## Focus + overlay nav

- `input::set_focused` (window `Focused` events): unfocused, `Sources::merged` drops gamepads + BLE (script still drives: a scripted window may sit in the background) and the pad settings trigger is ignored. Default true (headless).
- The settings overlay never sees the game bindings: `Sources.nav` = `gamepad_nav_pad` (fixed South/East/Start/d-pad/left stick) merged with BLE.
